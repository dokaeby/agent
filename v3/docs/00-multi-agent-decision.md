# 멀티에이전트가 정말 필요한가? — 의사결정 프레임워크

> 이 문서는 "멀티에이전트가 정말 필요한가를 먼저 따져보는 습관"을 위한 가이드.
> 멀티에이전트는 강력하지만, 항상 정답은 아니다.

## 단일 에이전트로 충분한 경우

다음 중 하나라도 해당하면 **단일 ReAct 루프(v1 방식)로 충분**하다:

- 작업이 선형적이다 (A→B→C 순서로 진행, 분기가 없음)
- 컨텍스트가 하나의 프롬프트에 들어간다
- 병렬화 이점이 없다 (각 단계가 이전 결과에 의존)
- 지연시간이 중요하지 않다 (순차 실행으로 충분히 빠름)

**예**: "이 코드의 버그를 찾아줘" → 단일 에이전트가 파일 읽고 분석하면 끝.

## 멀티에이전트가 필요한 경우

다음 중 **2개 이상** 해당하면 멀티에이전트를 고려한다:

| 조건 | 이유 |
|---|---|
| **병렬화 가능** | 서로 독립적인 작업을 동시에 처리해 wall-clock 시간 단축 |
| **역할 분리가 명확** | 각 역할의 시스템 프롬프트/도구/권한이 다름 |
| **검증/비평이 필요** | 생성자와 평가자가 분리되어야 품질이 올라감 |
| **컨텍스트 한계** | 한 프롬프트에 모든 정보를 넣기 어려울 때 |
| **재시도/피드백 루프** | 실패 시 특정 단계만 재실행하고 싶을 때 |

## 이 프로젝트에 적용

**서비스**: 리서치 주제 → 리포트 생성

| 에이전트 | 역할 | 패턴 |
|---|---|---|
| Planner | 주제를 3-5개 하위 질문으로 분해 | Plan-and-Execute |
| Researcher ×N | 각 하위 질문을 병렬 조사 | 병렬 서브에이전트 |
| Writer | 조사 노트를 바탕으로 초안 작성 | — |
| Reviewer | 초안을 채점하고 피드백 | Reviewer/Critic |
| Publisher | 최종 포맷팅 | — |

**멀티에이전트가 필요한 이유**:
1. **병렬화**: 5개 하위 질문을 동시에 조사 → 순차 대비 ~5배 빠름
2. **역할 분리**: researcher는 read 도구만, publisher는 write 도구만
3. **비평 루프**: writer가 자기 글을 검수하면 자기 편향 — reviewer 분리가 필수
4. **컨텍스트**: 각 researcher는 자기 질문만 보고 답하므로 프롬프트가 작음

**단일 에이전트였다면**: 모든 하위 질문을 순차 조사하고, 자기 초안을 자기가 채점 — 품질 저하 + 느림.

## 안티패턴 — 멀티에이전트가 오히려 해로운 경우

- **과도한 분해**: 2단계 작업을 5개 에이전트로 나누면 조율 비용이 이득을 초과
- **에이전트 간 의존성**: A→B→C→D 직렬이면 병렬 이점 없음
- **컨텍스트 손실**: 각 에이전트가 이전 결과를 요약하면서 정보 손실
- **비용 증폭**: N개 에이전트 × M턴 = 비용이 곱으로 증가 (BudgetTracker 필수)

## 판단 체크리스트

새 기능을 멀티에이전트로 구현하기 전에:

- [ ] 이 작업의 어느 부분이 병렬화 가능한가?
- [ ] 각 에이전트의 역할/도구/권한이 명확히 다른가?
- [ ] 단일 에이전트로는 해결 불가능한 품질 문제가 있는가?
- [ ] 비용 상한(BudgetTracker)과 타임아웃을 설정했는가?
- [ ] 실패 시 어느 단계부터 재시도할지 명확한가?
- [ ] 정말 멀티에이전트가 필요한가, 아니면 단순한 순차 파이프라인인가?

**정답은 없다.** 작은 작업은 단일 에이전트가, 복잡한 워크플로우만 멀티에이전트가 적합하다.
